Some work takes longer than a web call should wait: a video, a big batch, a workflow. Those operations answer **`202 Accepted`** with something to ask later, and you **poll** it.

There are two:

| You start it with | You poll it with | It ends as |
|---|---|---|
| `POST /tools/{tool}` | `GET /tools/runs/{run_id}` | `succeeded`, `failed`, `timeout` or `cancelled` |
| `POST /workflow-instances/{id}/api/requests` | `GET /workflow-instances/{id}/api/requests/{request_id}` | `succeeded` or `failed` |

## Tools: answer now or later

`POST /tools/{tool}` waits for the result up to `timeout_ms` (5000 ms by default).

- Finished in time: `200` with the result.
- Not yet: `202` with a `run_id` and a `poll_path`.

```python
import os

BASE = "https://api.wesog.com/api/v1"
headers = {"X-API-Key": os.environ["WESOG_API_KEY"]}

import time, requests

r = requests.post(f"{BASE}/tools/image_tag", headers=headers,
                  json={"image_url": "https://example.com/p.jpg", "timeout_ms": 3000})
while r.status_code == 202:
    time.sleep(1.5)
    r = requests.get(f"{BASE}/tools/runs/{r.json()['run_id']}", headers=headers)
print(r.json())
```

Poll every 1 to 2 seconds. Cancel a run you no longer need with `POST /tools/runs/{run_id}/cancel`.

## Workflows: one request per file

`POST /workflow-instances/{id}/api/requests` answers `202` at once with one `request_id` per file. Each file is processed on its own, so some can finish before others. `GET .../api/requests/{request_id}` answers `202` while it works and `200` with `results` when it has finished; if it failed, `status` is `failed` and `error` says why. See [Run a workflow](/new/guides/run-workflow).

## Webhooks

Wesog does **not** call your server when something finishes: you poll. This keeps your integration simple (no public address to open) and the state is always readable again, because a result stays available after you read it.

If you need to react to new content as it arrives, use [search alerts](/new/guides/alerts) (a notice, and optionally an email, when new files match a search), or make your program poll every few seconds only while it waits for something.

## If the connection drops

A `202` is a promise: the work continues even if you lose the connection. If you did not get the answer, **repeat the call with the same `Idempotency-Key`** (see [Idempotency](/new/concepts/idempotency)) and you get the same `run_id` or `request_id` back instead of starting the work twice.
